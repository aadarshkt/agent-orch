# Taste
- Prefers tightly condensed, summary-style output (e.g., one-to-two-line bullets) rather than long, verbose prose. Confidence: 0.95
- Prefers configuration-as-data (named presets/registries, e.g. YAML runtimes) so new tools/agents can be added quickly via data changes without code, seed, or frontend edits. Confidence: 0.8
- Separates per-run inputs (provided via frontend/dynamic forms, e.g. GitLab URLs, branch, prompt) from preconfigured server-side environment (Docker image, binary, skills, packages). Confidence: 0.85
- Prefers a single, self-contained YAML file as the source of truth per workflow, defining complete dependencies (runtimes, agents, workflow graph) in one place. Confidence: 0.9
- Wants a one-to-one mapping between YAML config and UI components so forms render automatically from the schema. Confidence: 0.7
- Draws the code/data boundary at the executor class: it defines the agent type's shape (input_schema fields), while individual agent instances in YAML only supply values. Adding an instance is a data change; adding a new field is a one-time schema edit. Confidence: 0.7
- Wants explicit, verifiable inter-node artifact/dependency handoffs (e.g. a downstream node referencing the prior node's commit hash via artifacts, or a declared depends_on/artifact_ref) rather than relying only on implicit execution ordering. Confidence: 0.7
- Prefers to build conceptual understanding of a design/architecture first (mental models, "how does this work", step-by-step explanations) before committing to implementation, rather than jumping straight to a solution. Confidence: 0.7
- Wants end-to-end, step-by-step documentation that covers the complete lifecycle of a feature (create, register, use across UI/YAML, migration/seeding) rather than partial or concept-only write-ups. Confidence: 0.7
- Prefers explicit, ordered/phased task lists that break remaining work into a clear sequence rather than a flat or unprioritized set. Confidence: 0.7
- Prefers happy-path-first scaffolding: defer validation and hardening (use placeholder/stub entries for now) until the core flow works. Confidence: 0.7
- Treats Docker image packaging (build/push of a CLI binary + runtime + packages) as part of CLI agent onboarding, not just defining runtime presets. Confidence: 0.6
 Prefers the assistant to proactively generate additional open design questions/edge cases ("create more such questions") rather than only answering the question asked. Confidence: 0.7
- Prefers implementation work to be done on a separate feature branch that is merged into master/main later, rather than committing changes directly to the main branch. Confidence: 0.85
- Prefers batching remaining work: complete all outstanding phases/tasks and commit them in one go, rather than stopping for incremental check-ins or confirmations between phases. Confidence: 0.8
- Insists the full deliverable be produced even when underlying pieces aren't built — scaffold every part and mark what's missing inline in comments ("even if parts are not built, you can mention this in comments") rather than omitting nodes or deferring the file until the code exists, so the complete target workflow is visible in one place. Confidence: 0.75
- Expects reference/example workflow YAML configs to be updated in tandem with schema/executor changes so they demonstrate the new fields (with commented-out usage for optional ones). Confidence: 0.55
- When requesting project documentation, wants the project actually run or verified first, with the existing README edited when appropriate and setup/usage details reflecting the observed state. Confidence: 0.85
- Prefers development startup scripts to automatically terminate stale processes occupying configured service ports before launching services, while preserving custom port overrides. Confidence: 0.85
- Prefers baking all runtime dependencies/tooling (build tools, compilers, packages) into a single Docker image per agent rather than maintaining auxiliary package-install config in the runtime schema (e.g. removing the dead `packages` field from RuntimeConfig); one static image = one runtime. Confidence: 0.7
- Prefers removing dead/unused config fields from schema/code when nothing reads them, rather than leaving them in place. Confidence: 0.7
- When assessing readiness of an implementation, wants the assistant to proactively surface remaining gaps (scaling, cleanup, concurrency, secrets) and judge whether it's good enough for initial onboarding, not just answer the immediate question. Confidence: 0.7
- Wants GitLab sources for the CLI agent modeled as two distinct categories: repo URLs treated as workspaces (multiple, mountable working surfaces) vs. single-file URLs fetched from (possibly different) repos and used purely as read-only context. Confidence: 0.65
- Expects the workspace mount into the CLI container to be a true one-to-one, bidirectional mapping — file changes made inside the container are immediately reflected on the host workspace (and vice versa), not a one-shot copy. Confidence: 0.65
- Expects CLI-agent authentication to work non-interactively/headless (e.g. via credentials/secret mounts) since the agent runs inside a container, rather than relying on an interactive browser-based OAuth flow. Confidence: 0.6
- Wants the assistant to be opinionated and prescriptive — give a definitive recommendation ("just say whatever is required") rather than presenting a menu of options, asking which direction to take, or deferring the decision back to the user. Confidence: 0.75
- When designing reusable assets (e.g. skills), wants resolution to be declarative/addressable (repo + ref + path, pinned) instead of relying on a fixed directory convention, on the assumption that future repos won't follow today's layout. Confidence: 0.6
- Strongly prefers exactly one canonical way to do each thing ("if skills are required there's one way, if context is required there's one way"): a single reusable type/config shape per concern, with zero alternative formats, shorthand sugar, or dual code paths — even when that means a stricter, breaking change to existing schema/YAML. Confidence: 0.8
- When open design questions are surfaced, wants each one elaborated in detail — framed as a concrete fork, with what the current code already implicitly chose (grounded in file/line references) and its consequences — plus a recommended resolution, rather than a terse question list or a decision punted back to the user. Confidence: 0.6
- Prefers to see and approve a written implementation plan (goal, locked decisions, scope/out-of-scope, per-file changes, verification steps) before implementation begins, rather than jumping straight into code. Confidence: 0.65
- Wants encapsulation by component: all logic belonging to a given executor (e.g. a CLI agent executor) should live inside that executor class rather than being spread across separate helper modules. Confidence: 0.6
- Expects UI-driven authoring (chaining nodes in the frontend) and YAML to be two views of the same contract that are truly equivalent: the backend should consume only YAML when creating a workflow (one write/validation path), and the UI should generate that same spec rather than posting a separate JSON/DB-id-shaped payload. Confidence: 0.7
- Icon-free UI is a hard project rule ("Don't use icons anywhere. if you find it remove it."): no icon fonts, SVG icon sets, emoji, or unicode glyphs — replace them with typographic labels, text actions, color-coded kind tags, and status dots. Confidence: 0.85
- For developer tools, wants a refined, modern aesthetic: dark near-black surfaces, hairline borders, a single restrained accent color, mono-set uppercase micro-labels, and precise/restrained motion (no heavy gradients or emoji). Confidence: 0.65
- Expects deliberately chosen typography to actually load: imports fonts properly (self-hosted, dev-tool-appropriate pairing like a geometric sans for interface text plus a mono for code/labels) and calls out fallback-to-browser-default fonts as a visible bug to fix, not a cosmetic nit. Confidence: 0.65
- Dislikes abrupt UI state changes: wants active/highlight transitions to cross-fade smoothly (fade in and fade out over a longer duration) rather than snapping when a state flips — explicitly calling the snap "abrupt" and asking for the transition "to next box" to look good. Holds a high bar for *perceived* smoothness and will re-raise it ("still looks abrupt, can you make it smooth?") if a previous fix didn't land, so expects the root cause to be fixed (e.g. a front-loaded easing curve that pops then crawls) rather than simply lengthening durations or restyling. Confidence: 0.8
- Prefers the interface to have a single canonical styling source of truth (layered design tokens + one way to style) and to not introduce new dependencies or a second, competing styling system (e.g. leaving an installed-but-unused Tailwind unwired) when the existing approach works. Confidence: 0.7
- Prefers grouped/parallel elements to change state simultaneously rather than in a staggered sequence — explicitly rejects a sequential "lighting up in sequence" cascade ("doesn't look good") and asks for siblings to light at once. Confidence: 0.7
- When an effect feels familiar, expects the assistant to consider an established library / off-the-shelf solution rather than hand-rolling it from scratch ("I think I have seen these types of things elsewhere, maybe you can find some library for this"), while still valuing a clear rationale for whether to adopt it. Confidence: 0.6
- When filling in gaps in his own understanding, wants to be quizzed: to be asked targeted questions, have each answer graded with an explicit score (per-question breakdown, not just a single verdict), and then receive the full correct answers to every question. Confidence: 0.6
- Prefers successive questions-only rounds when studying a file/codebase: he asks for more questions before reading the previous round's answers, so longer answer write-ups should not replace giving him the next set of questions. Confidence: 0.65
- Favors the simplest working execution model over feature-completeness — e.g. explicitly choosing a sequential, linear workflow graph over parallel fan-out "for simplicity for now", even when the original design runs some steps concurrently. Confidence: 0.55
